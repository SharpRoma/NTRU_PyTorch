## Реализация и незавершённые этапы

`TorchNTRU` использует CPU INT64 и не вызывает SymPy для арифметики. Генерация/проверка ключей общая и использует SymPy. Порядок коэффициентов — от младшего к старшему; кольцо Z[x]/(x^N-1), центрирование одинаково у обоих backend. Новое кодирование не идентично историческому битовому формату; legacy-чтение вынесено отдельно.

Hailo-кандидат считает только r*h. По знаку r создаются два потока бинарных чанков. Открытый h разложен по битам в весах Conv2d 1×1. Частичные суммы ограничены 0..16; CPU восстанавливает результат INT64, добавляет m, выполняет mod q и центрирование. Один HEF соответствует одному открытому ключу.

| Подготовленный эксперимент | q | Cin | Cout | Кадров на полином | UINT8 вход+выход на полином |
|---|---:|---:|---:|---:|---:|
| N=17 | 256 | 32 | 144 | 4 | 704 байт |
| N=107 | 64 | 112 | 656 | 14 | 10 752 байт |

Числа трафика получены из формы графа; протокольные накладные расходы не включены. Для N=701/q=8192 тот же профиль требует 88 кадров и 864 512 байт на полином. Поэтому оценку передачи двух INT16-векторов из статьи нельзя применять к этому профилю.

`build.py` уже запускает worker напрямую на Linux, WSL не нужен. Однако его docstring и сообщение при отсутствии отчёта ещё ссылаются на WSL. `runtime.py` содержит устаревшую рекомендацию Windows-wheel при ошибке импорта. `README.md` частично называет ONNX будущей работой; `docs/hailo-research.md` сохраняет описание WSL-стадии. Эти фразы следует обновить вместе с реальным запуском Linux toolchain.

`dfc_worker.py` сохраняет HAR/HN, переведённые SDK-параметры, model script, калибровку, битовую эмуляцию, журнал и времена. Он всегда оставляет успешно скомпилированный граф в `compiled-unverified`, `extraction_supported=false`. Реального экстрактора эффективных весов, bias, округлений и насыщения нет. `hailo-admit` правильно отклоняет такой результат. `force_range_out=[0,255]` само по себе не доказывает тождественность квантования.

Профиль affine имеет рациональную проверку ошибки строго <1/2 и LUT-восстановление, но пока проверяется только на синтетических свидетельствах. Нет основания заполнять report/evidence исходными ONNX-весами или вручную выставлять `ready-for-admission`.

Текущий аппаратный pytest проверяет частичные суммы, 1000 случайных полиномов и несколько bytes-сообщений. В нём ещё нет явной проверки Unicode и повторного открытия реального устройства/очистки после реальной ошибки. Это требуется дополнить перед окончательным аппаратным заключением. Тесты с mock SDK подтверждают только код адаптера. Бенчмарк 1/8/32/128 блоков требует N>=64 из-за заголовка длины и предназначен для следующей стадии N=107, не для N=17.

## Следующий эксперимент и критерий завершения

1. Адаптировать установщик и установить DFC 3.33.0 в отдельное venv. Зафиксировать wheel hash, Python, resolved dependencies; получить успешный импорт ClientRunner. Для первого маленького графа проверить возможность CPU-режима, не считать GPU обязательным до проверки SDK.
2. В отдельном пустом `results/build-n17-ubuntu-unit-001` собрать существующий `results/compiler-experiments/n17/prepared` с `unit-v1`. Сохранить все промежуточные артефакты. Не запускать N=107 вместо разбора причины неудачи N=17.
3. По реальным данным DFC реализовать и проверить экстрактор арифметики. Если unit-v1 невозможен, отдельно исследовать affine с доказанной границей <1/2. Недостаток данных SDK означает unsupported, а не ослабление допуска. Успешная эмуляция на калибровке не является универсальным доказательством.
4. Подготовить Linux HailoRT/PyHailoRT и PCIe-драйвер версии 4.23, проверить ядро/подпись, scan и identify. Подтвердить архитектуру Hailo-8L и фактическую firmware. Обновление прошивки не выполнять автоматически.
5. После численного допуска проверить на устройстве все базисные векторы обоих знаков, ноль, полные/хвостовые чанки и предельные входы, >=1000 случайных полиномов. Требовать точного равенства частичных сумм и шифротекстов трёх реализаций при одинаковых ключах/m/r. Проверить Hailo→SymPy/Torch для пустых, Unicode, бинарных, многоблочных сообщений; повторное открытие и очистку после ошибки. Сохранить HEF/key hashes, версии и аппаратные журналы.
6. Только после точного N=17 повторить компиляцию, извлечение, допуск и аппаратную проверку для N=107. После точного N=107 измерять packing / transfer+call / recovery / total / load / compilation отдельно, batch 1/8/32/128; сохранять JSON/CSV. Ускорение не является условием корректности, энергоэффективность требует измерений мощности.
