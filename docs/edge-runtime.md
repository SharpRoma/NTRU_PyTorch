# Подготовка к Raspberry Pi при сохранении работы на ПК

> Исторический этап подготовки runtime на ПК. SparseNTRU и liboqs на ПК уже добавлены; N701 на Raspberry Pi уже прошёл аппаратную квалификацию. Актуальные границы и следующие задачи: [актуальный handoff от 9 ноября 2026](CODEX_HANDOFF_2026-11-09.md).

Реализован первый этап: ограничение памяти при численном допуске и отдельный облегчённый runtime. Алгоритмы CPU, ключи, шифротексты, HEF и формат результатов прежних бенчмарков сохранены. Честный расширенный CPU-baseline, статистический протокол будущей статьи и сам перенос на ARM остаются следующими этапами.

## Два окружения из одного исходного кода

Обычная установка проекта остаётся прежней: `pyproject.toml` по-прежнему требует SymPy и PyTorch. Работают существующие импорты, команды demo/trace/benchmark, подготовка и компиляция Hailo. Публичные CPU-backend загружаются лениво при обращении; импорт моделей, CLI или Hailo-движка больше не подтягивает PyTorch/SymPy, ONNX или vendor SDK.

Дополнительный runtime-wheel собирается из того же дерева `src/ntru_pytorch`, без копии алгоритмов и отдельной ветки. Его версия имеет суффикс `+edge`, обязательная Python-зависимость — NumPy `>=1.26,<2`; runtime-профиль ограничен Python 3.11/3.12. NumPy 1.26.4 поддерживает Python до 3.12 ([официальные release notes](https://numpy.org/doc/1.26/release/1.26.4-notes.html)). Это ограничение нужно учитывать при выборе Python на Pi; desktop-метаданные не сужались. Сохраняются CLI entry point и лицензия MIT. Extras `desktop` и `export` позволяют явно добавить вычислительные или экспортные зависимости. По умолчанию они не устанавливаются.

```bash
cd /home/sharproma/PycharmProjects/NTRU_PyTorch
.venv/bin/python tools/build_runtime_wheel.py --output results/NEW-EDGE-WHEEL
```

Требуется рабочее окружение сборки с pip и setuptools, поддерживающим сборку wheel. Команда не скачивает зависимости сборки (`--no-build-isolation --no-deps`) и не устанавливает ничего в текущую `.venv`. Каталог вывода должен быть новым. Вместе с wheel сохраняется manifest с хешами исходников и пакета.

На целевой машине создать отдельное окружение, затем установить полученный wheel обычным pip, который подберёт NumPy для её архитектуры. Например, для текущей версии:

```bash
python3 -m venv .venv-edge
.venv-edge/bin/python -m pip install /path/to/ntru_pytorch-0.1.0+edge-py3-none-any.whl
.venv-edge/bin/python -m pip check
```

Оба профиля используют имя пакета `ntru-pytorch`, поэтому предназначены для разных venv. Текущая `.venv` ПК сохраняется. HailoRT и PyHailoRT 4.23.0 нужной архитектуры устанавливаются отдельно; wheel проекта не содержит драйвера, SDK или firmware. Само наличие pure-Python wheel не подтверждает совместимость нативных библиотек на ARM. На Raspberry Pi нужно заново проверить их наличие, ABI, архитектуру HAILO8L и firmware.

В runtime без CPU-зависимостей использовать целевые импорты, например `from ntru_pytorch.hailo import HailoEncryptor`. Запрос CPU-backend, генерации ключей или полной кросс-квалификации требует соответствующих зависимостей. Для измерений CPU и NPU на Pi планируются отдельные процессы/окружения, чтобы память импортированного PyTorch не включалась в измерение Hailo.

## Проверка численных свидетельств с ограниченной памятью

Старый N=701 `numeric-evidence.npz` содержит матрицу строковых точных коэффициентов размером 514.34 МиБ. Теперь:

- SHA256 вычисляется порциями по 1 МиБ, без чтения файла целиком в Python-объект.
- Матрица читается по одной строке прямо из существующего NPZ, в том числе DEFLATE-сжатого.
- Рациональные строки передаются неизменёнными в прежний `prove_affine`: проверяются все коэффициенты, строгая ошибка <1/2, насыщение и аккумуляторы.
- Unit-профиль также сравнивает строки точных весов последовательно; bias читается отдельно с ограничением размера.
- Заголовки, размеры и типы проверяются до выделения памяти. Объектные/pickle-массивы, дубликаты обязательных членов архива и повреждённые данные отклоняются.

Поддерживается текущий DFC-формат: NPY 1.0/2.0, примитивные C-order массивы чисел или рациональных строк, строка не более 4 МиБ, bias не более 4 МиБ. Fortran-order и другие неподдерживаемые представления явно отклоняются без fallback к полной загрузке. В памяти по-прежнему остаётся небольшая бинарная матрица `BinaryScheme` и служебные данные; расход памяти не является константой при произвольном росте N.

Исходные архивы и их хеши не менялись. Новый компактный формат хранения пока не вводился: файл по-прежнему занимает около 515 МиБ на диске, но не загружается целиком в RAM. Полный массив по-прежнему можно передать напрямую в `prove_affine` для контрольных экспериментов на ПК.

## Измерение памяти на ПК, 8 ноября 2026

Данные: `results/edge-preparation-2026-11-08-001/`. Каждый профиль выполнялся отдельным процессом. Старый код взят из сохранённого снимка предыдущего аппаратного эксперимента `n701-host-optimization-2026-11-08-001/source/src`; путь реально импортированного загрузчика записан в отчёте.

| Сценарий N=701 | Пик RSS, МиБ | Область проверки |
|---|---:|---|
| Старый desktop-процесс | 1089.67 | Импорт + полная проверка артефакта, без устройства |
| Новый изолированный runtime | 55.78 | Импорт + полная проверка того же артефакта, без устройства |
| Новый процесс под лимитом 768 МиБ, swap=0 | 62.58 | Полная проверка + открытие Hailo + один реальный нулевой полином |
| Новый процесс под тем же лимитом, партия 128 | 96.71 | Полная проверка + реальное шифрование 128 блоков + независимая INT64-свёртка |

Второй сценарий выполнялся в изолированном окружении, где PyTorch/SymPy отсутствовали; NumPy 1.26.4 переиспользован из локальной установки через symlink для автономного теста без сети. Финальный wheel установлен, исходники внутри него сверены с рабочим деревом, лицензия сохранена, `pip check` успешен. Аппаратные сценарии использовали обычную `.venv` с установленным HailoRT, но PyTorch/SymPy в процессы не импортировались. На партии 128 подтверждены 1024 кадра, вход 720896 байт, выход 9338880 байт и точное совпадение с независимой INT64-свёрткой. Единичное время из профиля памяти не заменяет статистический бенчмарк.

Лимит задан временной пользовательской systemd scope: MemoryMax=805306368, MemorySwapMax=0; OOM/OOM-kill не зарегистрированы. Постоянные настройки ОС не менялись. Cgroup учитывает разделяемые страницы и файловый кэш иначе, чем RSS; это ограничение группы процессов, а не эмуляция всей Raspberry Pi с её ОС. Проверка выполнена на x86 Ubuntu, поэтому ни время, ни расход памяти ARM из неё не следуют.

Время численной проверки в этих одиночных диагностических запусках — около 47–54 с; статистический вывод об ускорении старта не делается. Проверка доказательства не отключена и не заменена доверием к короткому сертификату.

Профилировщик сохраняет wall time стадий, текущий/пиковый RSS, загруженные backend, источник загрузчика и, при доступности, показатели cgroup:

```bash
.venv/bin/python tools/profile_hailo_memory.py \
  --artifact results/admitted-n701-ubuntu-affine-001 \
  --output results/NEW-MEMORY.json
```

Флаг `--open-device` добавляет открытие устройства и один нулевой аппаратный вызов. В отчёте он явно помечен как smoke-тест, `hardware_qualification=false`; он не заменяет 1000 случайных полиномов и кросс-проверки. Дополнительный `--blocks 128` измеряет память полного `encrypt_bytes` с нормальными r, seed=42, затем сверяет шифротекст с независимой NumPy INT64-свёрткой без импорта CPU-backend. Подготовка и проверка результата выделены в отдельные стадии. Скрипт требует Linux из-за единиц RSS и `/proc`, отказывается перезаписывать прежний файл и сохраняет последнюю стадию при исключении.

## Совместимость и аппаратные свидетельства

Прежний `demo --preset moderate --seed 42` на ПК прошёл четыре сочетания шифрования/расшифровки SymPy и PyTorch. Программные тесты сравнивают потоковый и полный математический допуск, сжатые/несжатые NPZ, числовые/строковые коэффициенты, повреждённые формы и заголовки, object dtype, неподдерживаемую раскладку и огромные объявления dtype без выделения памяти. Проверены публичные ленивые импорты и отсутствие незапрошенных backend.

Полный программный набор: **102 passed, 1 аппаратный тест deselected**; Ruff и `git diff --check` прошли. Отдельно выполнена реальная аппаратная квалификация после изменения загрузчика: N=17 — 1048 проб, N=107 — 1238, N=701 — 2500. В каждом случае 1000 случайных полиномов, точные частичные суммы/произведения, совпадение SymPy/PyTorch/Hailo, кросс-расшифровка сообщений, три открытия сессии и очистка после контролируемого исключения на хосте. Отчёты `n17-hardware.json`, `n107-hardware.json`, `n701-hardware.json` имеют `status=passed`, `hardware_tested=true`, `exact=true`.

Итоговый пакет находится в `runtime-wheel-final/`; промежуточные сборки в других подкаталогах сохранены как материалы эксперимента. В каталоге результатов также находятся отчёты памяти и cgroup, логи тестов/demo/аппаратной проверки, manifest сборки, проверка установки и `summary.json` с хешами исходников. Снимок старого загрузчика и его происхождение указаны в `baseline-memory.json`.

Ни программные тесты, ни ограничение памяти на x86 не являются подтверждением работы на Raspberry Pi. После переноса остаются ARM64 preflight, полная аппаратная квалификация на самой плате, наблюдение RAM/swap/температуры/частот и отдельное сравнение CPU/NPU. Старые desktop-эксперименты и [результат оптимизации CPU вокруг Hailo](hailo-host-processing.md) сохранены.
