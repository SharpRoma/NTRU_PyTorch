# Запуск Hailo NTRU на Ubuntu

> Журнал нескольких последовательных состояний Ubuntu. Разделы про ещё не загруженный драйвер, MOK и предстоящие N17/N107 — исторические. Текущее состояние, включая liboqs и успешный Pi N701: [актуальный handoff от 9 ноября 2026](CODEX_HANDOFF_2026-11-09.md). Secure Boot/TPM отключены пользователем; настраивать их дальше не требуется.

Обновлено 7 ноября 2026 года. DFC 3.33.0 установлен и работает на CPU с Python 3.12.3. **N=17 и N=107 собраны, прошли численный допуск и точную аппаратную квалификацию на Hailo-8L.** Подтверждено выполнение кандидата r*h на NPU с восстановлением/редукцией и расшифровкой на CPU. Secure Boot и TPM намеренно отключены пользователем; их настройка исключена из дальнейшего плана.

## Что выполнено

- `tools/setup_dfc_ubuntu.sh` адаптирован под Ubuntu 24.04/Python 3.12. До системных изменений проверяется SHA256 DFC wheel. `--check` выполняет предварительную проверку, `--resume` продолжает только окружение с совпадающей записью происхождения wheel, без удаления venv. Добавлены CMake и отсутствующая в metadata SDK зависимость `typeguard==2.13.3`.
- DFC находится в `/opt/ntru-dfc`; `ClientRunner` импортируется без диагностического overlay, `pip check` проходит. Разрешённые версии сохранены в `results/ubuntu-implementation-2026-11-07/dfc-requirements-resolved.txt`. Первые неудачные журналы сохранены: сначала отсутствовал CMake, затем typeguard.
- Драйвер 4.23.0 из официального тега собран без изменений исходников под `7.0.0-42-generic`. Версия модуля и vermagic проверены; первоначальный локальный модуль ещё не подписан и не загружен. Commit драйвера: `ce1087bfe8132c99b41374e3128fc78612a3f492`.
- HailoRT 4.23.0 собран из официального commit `08f088d3b443c7846af067269ce998c6d5d91449`. Локальная библиотека и CLI находятся в `results/toolchain/hailort-4.23.0-local`; PyHailoRT cp312 собран и установлен в проектное `.venv`. `pip check` проекта проходит. Системную установку библиотеки и DKMS выполняет отдельный скрипт ниже.
- Исправлено создание рабочего каталога оптимизации SDK. Калибровка теперь явно использует все подготовленные кадры; оптимизация уровня 0 по умолчанию использовала только 64. Для N=17 полный набор содержит 1044 кадра. Worker сохраняет native-выходы, traceback, численные параметры до и после компиляции и все прежние HAR/HN/логи.

## Реальный численный результат N=17

Подготовленный ключ/ONNX взят из `results/compiler-experiments/n17/prepared`: N=17, p=3, q=256, Cin=32, Cout=144. Ключ не изменялся.

Первый unit-вариант `results/build-n17-ubuntu-unit-002` собран, sample error в эмуляторе равен нулю, но остаётся `compiled-unverified`. Фактические веса 0/127, сдвиг MAC=1 и APU-преобразование не соответствуют прежнему строгому контракту тождественного unit-квантования. Нулевую ошибку на выборке не использовали для подмены этого контракта.

Отдельный affine-вариант задаёт диапазон входа [0,255] и выхода [0,32]. Входные коды остаются 0/1, выходные суммы восстанавливаются точной рациональной LUT. Финальный проверенный каталог сборки: `results/build-n17-ubuntu-affine-003`; допущенный артефакт: `results/admitted-n17-ubuntu-affine-003`.

| Свойство | Фактическое значение |
|---|---|
| HEF SHA256 | `8a00dd51f08a47854833947070c927f0c41cf7476d1be22a96daca0897837ed6` |
| Вход / выход | `ntru_binary/input_layer1` / `ntru_binary/conv1`, UINT8 |
| Масштабы | вход 1; выход точно `8421505/67108864`; zero points 0 |
| Целые веса / сдвиг | 0 или 127; округление каждого произведения после сдвига на 1 даёт 0 или 64 |
| Аккумулятор | фактический signed 16-bit; максимум на допустимом кадре не более 1024 |
| APU | mantissa 515, encoded exponent 2, exponent bias 7, final shift 3; offsets и bias нулевые |
| Максимальная граница ошибки | `277910427/1073741824`, около 0.258824255, строго < 1/2 |
| Численная эмуляция | все 1044 кадра после LUT точно совпали с целочисленным эталоном |
| Аппаратный результат | После установки драйвера проверка прошла; см. раздел аппаратных результатов ниже |

Экстрактор `src/ntru_pytorch/hailo/dfc_extract.py` поддерживает только наблюдённую топологию input→Conv1×1→output с a8_w8_a8, одним квантовым диапазоном, нулевыми bias/offsets, тождественным кодированием бинарного входа и линейным APU. Неизвестные операции/параметры отклоняются. Параметры извлекаются из настоящего compiled HAR и SDK-модели; исходные ONNX-веса не выдаются за эффективные.

Для бинарных входов округление каждого произведения вычисляется точно. Эффективные коэффициенты далее выводятся из целых MAC-весов, mantissa/exponent APU и реального выходного масштаба. Учитывается первая стадия округления; последняя консервативно покрывается полным выходным LSB. Проверяются границы аккумулятора, внутренних clip1/clip2 и области APU-сегментов. Неотрицательность целочисленного тракта даёт структурную нижнюю границу 0 перед выходным округлением; она не выводится из уже насыщенных выходов выборки.

Host-проверка заново выполняет рациональное доказательство для всех допустимых бинарных кадров с <=16 активными коэффициентами. Она учитывает реальные 16- либо 32-битные аккумуляторы и допускает дополнительные доверенные границы до выходного округления. Затем `hailo-admit` читает **сам HEF через HailoRT**, проверяя имена/формы/UINT8/scales/zero points без открытия платы. Исходный unit-контракт не ослаблен.

Свидетельства и compiler-report по-прежнему требуют доверия к экстрактору и семантике SDK. Это не аппаратная аттестация. В отчёте сохранены хеши SDK-исходников использованных atomic operations, экстрактора, compiled HAR и численных параметров.

## Системная установка и Secure Boot

Установка уже выполнена; команды этого раздела сохранены для воспроизводимости, повторять установщик на существующем DKMS-дереве не требуется.

Включён Secure Boot. `tools/install_hailo_linux.sh` проверяет pinned commits, чистоту исходников, версию/ядро собранного драйвера и SHA256 firmware-файла. Затем устанавливает HailoRT в `/usr/local`, создаёт DKMS-модуль, обеспечивает его подпись и устанавливает udev-правило с владельцем по SUDO_UID и правами 0600: устройство доступно только пользователю, запустившему sudo. Исходное правило производителя с правами 0666 не устанавливается. Скрипт отказывается перезаписывать другой firmware-файл и существующее дерево DKMS без разбора состояния.

```bash
sudo bash /home/sharproma/PycharmProjects/NTRU_PyTorch/tools/install_hailo_linux.sh
```

Файл `hailo8_fw.4.23.0.bin` скачан по URL из официального `download_firmware.sh`; SHA256 `1ba9528972091ec17bebc0dc7ea2e6f4449efe70664890f6387ccbc7b60626ee`. Драйвер использует его для загрузки в RAM при инициализации устройства. Команды записи firmware во flash не выполняются. При наличии другого файла скрипт останавливается.

Если MOK ещё не зарегистрирован, скрипт оставляет подписанный драйвер установленным и останавливается до `modprobe`. Он выводит команду `sudo mokutil --import /var/lib/shim-signed/mok/MOK.der`. Одноразовый пароль задаётся пользователем в терминале; регистрация завершается пользователем через MOK Manager при следующей перезагрузке. Автоматических перезагрузок, смены ядра и отключения Secure Boot нет. После регистрации проверить загрузку модуля, `/dev/hailo0`, scan и identify; при несовпадении архитектуры Hailo-8L или firmware 4.23.0 аппаратный этап остановить.

## Аппаратная квалификация и следующий переход

`hailo-demo` теперь выполняет полную квалификацию: >=1000 случайных полиномов, ноль, все базисные векторы обоих знаков, каждый полный/хвостовой чанк, плотные и чередующиеся предельные входы; точные шифротексты и кросс-расшифровку для пустых, Unicode, бинарных и многоблочных сообщений. Проверяются три открытия настоящей сессии и освобождение ресурсов после контролируемого исключения на хосте **после успешного inference**. Это не испытание восстановления после физического отказа PCIe. Адаптер сверяет архитектуру платы и firmware и сохраняет их в отчёте.

После готовности драйвера:

```bash
/home/sharproma/PycharmProjects/NTRU_PyTorch/.venv/bin/python -m ntru_pytorch hailo-demo \
  --artifact /home/sharproma/PycharmProjects/NTRU_PyTorch/results/admitted-n17-ubuntu-affine-003 \
  --private-key /home/sharproma/PycharmProjects/NTRU_PyTorch/results/compiler-experiments/n17/private.json \
  --report /home/sharproma/PycharmProjects/NTRU_PyTorch/results/ubuntu-implementation-2026-11-07/n17-hardware.json
```

Только после успешной аппаратной квалификации N=17 строить N=107 в новом каталоге, повторять численный допуск и аппаратную квалификацию. Затем измерять 1/8/32/128 блоков. Бенчмарк сохраняет измеренное время компиляции из метаданных сборки, если оно доступно; внутреннюю аппаратную задержку или энергию по-прежнему не выдумывает.

Программные проверки после изменений: 59 passed, 1 аппаратный deselected за 87.79 s, включая slow; затем 23 быстрые Hailo-проверки прошли после последних изменений. Ruff и синтаксис обоих shell-скриптов проверены. Программные результаты и эмуляция не подтверждают работу NTRU на NPU.

## Состояние сразу после системной установки до перезагрузки

HailoRT установлен в `/usr/local`, DKMS сообщает `hailo_pci/4.23.0, 7.0.0-42-generic, x86_64: installed`. Модуль подписан ключом `sharproma-ubuntupc Secure Boot Module Signature key`; udev-правило задаёт OWNER=1000, MODE=0600. Ключ `/var/lib/shim-signed/mok/MOK.der` пока не зарегистрирован, поэтому `modprobe` возвращает `Key was rejected by service`, а `/dev/hailo0` отсутствует. Следующий шаг — регистрация MOK через терминал и MOK Manager при ручной перезагрузке. Повторная установка драйвера не требуется.

В этой версии mokutil команда `--test-key` вернула exit 0 одновременно с текстом `is not enrolled`. Проверка установщика исправлена: один exit code больше не считается подтверждением регистрации; неизвестный или отрицательный ответ останавливает загрузку модуля.

## Диагностика задержки рабочего стола

В текущем boot журнал фиксирует открытие пользовательской сессии на 21.625 s и запуск GNOME Shell на 157.804 s: пауза около 136 s. На 45.016 s xdg-desktop-portal запросил GNOME-backend до готовности graphical-session.target; зависимость не запустилась. Затем зарегистрированы тайм-ауты settings/file chooser proxy и самой службы portal на 135.110 s. GNOME-сессия стала активна на 158.059 s. Полную задержку пять минут эти записи не устанавливают; конкретная первопричина преждевременного запроса portal ещё не доказана.

Hailo инициализировался на 5.77 s, загрузка firmware заняла 161 ms, `/dev/hailo0` создан на 5.944 s. systemd-analyze сообщил общую загрузку системы 32.542 s с учётом firmware/loader. Длительная пауза наблюдается на этапе графического сеанса, а не инициализации платы. Настройки рабочего стола, Snap, порталов и NVIDIA не менялись. Исходный журнал и пояснение сохранены в `results/ubuntu-implementation-2026-11-07/login-diagnostic/`.
