# Усиленный CPU-baseline для сравнения с Hailo

Добавлен отдельный `SparseNTRU`, сохраняющий прежние модели ключей, шифротекстов и байтовый формат. `SympyNTRU` и `TorchNTRU` не заменены. Их исторические результаты остаются сравнением именно этих реализаций. Новый backend использует разреженное тернарное r; это более сильный NumPy CPU-baseline, но не утверждение о самой быстрой возможной реализации на CPU или об оптимизированных C/ASM/NTT-библиотеках.

## Два точных ядра

- `shift-sum`: подготовленный удвоенный вектор h; циклические сдвиги прибавляются/вычитаются по ненулевым позициям r. Память подготовки O(N), работа O(N·nnz(r)).
- `cached-shifts`: заранее подготовлены все N циклических сдвигов h; выбранные строки отдельно суммируются для положительных/отрицательных позиций. Память подготовки O(N²), работа O(N·nnz(r)). Для N=701 удерживаемые массивы занимают 3 936 816 байт, для shift-sum — 16 824 байта.

Данные и аккумуляторы INT64, без float, FFT, GPU или NPU. До подготовки проверяется консервативная граница N·max|h| ≤ 2^63−1; все промежуточные суммы подмножеств и линейное произведение для трассировки также укладываются в эту границу. До добавления сообщения произведение редуцируется по q. Для расшифровки используется независимая плотная NumPy INT64-свёртка с собственной проверкой границ.

`prepare(key)` создаёт кэш одного неизменяемого публичного ключа и возвращает время подготовки и размер массивов. Равный ключ переиспользует кэш; другой ключ перестраивает его. Кэш не зависит от сообщения или r. При ошибке подготовки предыдущий кэш сохраняется. По умолчанию удерживаемые массивы ограничены 64 МиБ; это не предел RSS процесса, поскольку есть временные индексные массивы и данные сообщений. Для больших N можно явно выбрать shift-sum или другой бюджет.

Код ориентирован на последовательные вызовы одного экземпляра. Он исследовательский и не сертифицирован как constant-time: выбор позиций r зависит от данных. Результаты относятся к арифметике и API текущей схемы проекта, не к стандартизованному NTRU KEM или доказанной стойкости параметров.

## API и окружения

```python
from ntru_pytorch import SparseNTRU

cpu = SparseNTRU(kernel="cached-shifts")
preparation = cpu.prepare(public_key)  # отдельно от основного таймера
ciphertext = cpu.encrypt_bytes(public_key, message, r_polys=rs)
assert cpu.decrypt_bytes(private_key, ciphertext) == message
```

Также поддерживаются `encrypt_poly`, `encrypt_polys`, текстовые методы и трассировка. События `product`/`cyclic`/`ciphertext` при шифровании и `product`/`centered`/`message` при расшифровке совпадают со стандартными CPU-backend. Отладочный trace вычисляет полное линейное произведение дополнительно и не используется в замерах.

CPU и Hailo используют общий точный массивный кодек/валидатор из `array_api.py`; арифметические ядра разные. Старые внутренние импорты из `hailo.host` сохранены как aliases. Импорт `SparseNTRU` загружает NumPy, но не SymPy, PyTorch или Hailo. Для SparseNTRU используется явный импорт, исторический wildcard-набор экспортов сохранён без новой зависимости NumPy. Обычная установка ПК сохраняется; optional extra `cpu-sparse` добавляет NumPy. Runtime-wheel также может использовать этот backend без desktop-зависимостей после пересборки из актуальных исходников.

## Воспроизведение измерений

CPU-only режим без платы, SymPy и обязательного PyTorch:

```bash
cd /home/sharproma/PycharmProjects/NTRU_PyTorch
.venv/bin/python tools/benchmark_sparse_cpu.py \
  --public-key results/admitted-n701-ubuntu-affine-001/public.json \
  --private-key results/compiler-experiments/n701-active16-2026-11-08/private.json \
  --seed 42 --runs 20 --warmup 3 \
  --output results/NEW-CPU-RUN/benchmark
```

Для добавления прежнего PyTorch: `--include-torch --torch-threads 6`. CPU-only инструмент проверяет соответствие ключей, шифротексты через плотную INT64-свёртку и расшифровку; сохраняет JSON/CSV, подготовку ключей, сырые времена, медианы/p95, блоки/с, полезные байты/с и fingerprints файлов ключей. Он всегда помечен `hardware_tested=false`, устройство не открывает.

Общий аппаратный запуск с четырьмя измеряемыми вариантами:

```bash
.venv/bin/python -m ntru_pytorch hailo-benchmark \
  --artifact results/admitted-n701-ubuntu-affine-001 \
  --private-key results/compiler-experiments/n701-active16-2026-11-08/private.json \
  --packing active16-v1 --host-processing optimized \
  --skip-sympy-timing --include-sparse-cpu --torch-threads 6 \
  --seed 42 --runs 20 --warmup 3 \
  --output results/NEW-COMPARISON/benchmark \
  --report results/NEW-COMPARISON/cli-report.json
```

Новый флаг необязателен: прежний набор backend и поведение по умолчанию сохранены. CPU-ядра используют NumPy INT64-редукции, не BLAS matmul; `--torch-threads` управляет только PyTorch. Параллельная реализация sparse CPU в этом этапе не добавлялась.

До измерений вызывается явный prepare для CPU-ключа и открывается сессия Hailo. В таймере остаются проверки API, кодирование сообщения, поиск ненулевых позиций, арифметика и создание Ciphertext. Генерация ключей/r, подготовка постоянного ключа/HEF, проверки правильности и файловый ввод-вывод исключены. Для каждого размера партии используется один заранее подготовленный корпус, повторяемый при прогревах и измерениях, одинаковый для всех backend. Это warm-cache опыт; смена входного корпуса между итерациями и многопоточный native CPU требуют отдельного протокола.

## Корректность и исходная точка

Программно проверены N=17/107/701 и оба ядра: минимум 1000 случайных полиномов для каждого N/ядра, нулевые, базисные, плотные, хвостовые и граничные входы 15/16/17, полные трассировки, сообщения и кросс-расшифровка, другие p/q, ошибки типов/размеров, переполнение, лимит кэша, смена ключа и CPU-only запуск без других backend. Полный набор: 121 passed, 1 аппаратный тест deselected. Дополнительные 6 тестов кэша и 34 финальные проверки Sparse/edge/import compatibility прошли; Ruff и git diff --check прошли.

Материалы: `results/sparse-cpu-baseline-2026-11-08-001/`. `cpu-pilot.json` и `cpu-only.json` — программные измерения, не аппаратные свидетельства. Основное сравнение выполнено двумя независимыми запусками; внутри каждого процесса чередовались все четыре измеряемых backend с реальным Hailo-8L; в каждом повторяются 2500 аппаратных проб и кросс-проверки SymPy/PyTorch/Sparse/Hailo. Исторические HEF и ключи сохранены.

## Измеренный результат N=701 на текущем ПК

Выполнены два независимых процесса, seed=42, 6 потоков PyTorch, 3 прогрева и 20 измерений каждого backend на каждой партии. Основная таблица — медианы объединённых **40** измерений, а не среднее медиан. Сохранены 640 измерений; пилот и CPU-only результаты в таблицу не смешивались.

| Блоков | PyTorch CPU, мс | Shift-sum CPU, мс | Cached-shifts CPU, мс | Hailo, мс | Hailo / cached CPU |
|---:|---:|---:|---:|---:|---:|

| 1 | 3.086 | 0.550 | 0.473 | 1.485 | 3.137× |
| 8 | 24.252 | 4.019 | 3.451 | 9.056 | 2.624× |
| 32 | 96.426 | 15.865 | 13.572 | 25.913 | 1.909× |
| 128 | 386.262 | 62.832 | 53.838 | 105.812 | 1.965× |

Последний столбец больше единицы означает, что **Hailo медленнее cached CPU**, а не ускорение NPU. Оба новых CPU-варианта быстрее Hailo на всех проверенных партиях в каждом из двух запусков. На 128 блоках cached CPU быстрее прежнего PyTorch примерно в 7.17×, аппаратного пути — в 1.97×. Для этой конфигурации фиксированный публичный ключ эффективно используется на CPU; прежнее ускорение Hailo относительно PyTorch нельзя обобщать на CPU в целом.

На 128 блоках медианы отдельных запусков:

| Раунд | PyTorch, мс | Shift-sum, мс | Cached-shifts, мс | Hailo, мс | Hailo / cached CPU |
|---:|---:|---:|---:|---:|---:|
| 1 | 386.912 | 63.091 | 54.179 | 105.775 | 1.952× |
| 2 | 384.829 | 62.624 | 53.496 | 105.812 | 1.978× |

Для Hailo на 8 блоках отмечен заметный межзапусковый разброс: 10.709 и 7.495 мс; объединённая медиана 9.056 мс описывает именно эти данные. Они сохранены без отбора. При этом cached CPU быстрее в обоих раундах (3.498 и 3.437 мс). Доверительные интервалы не оценивались; это два warm-corpus запуска на одном экспериментальном ключе, не окончательный статистический протокол статьи.

Выигрыш относительно старого PyTorch относится к готовой реализации с разреженным ядром и пакетным API, не является измерением только одного математического ядра.

### Точность, память и границы вывода

В обоих аппаратных раундах HAILO8L / runtime и firmware 4.23.0; перед замерами пройдены 2500 аппаратных проб, включая 1000 случайных полиномов, и совпадение шифротекстов/кросс-расшифровка с SymPy, PyTorch и обоими Sparse CPU на партиях 1/8/32/128. HEF SHA256 `a8db2b54e0eb7f519959f808f1c0312bc820567eb5bf95e7a40cc01617b6af63`, канонический SHA256 ключа `54e0c7e244eb1c93c4761b4b99a98e0e8123a13f17663754931650ca08042f03`. Передача не менялась: 8 кадров на полином, на 128 блоках вход 720896 и выход 9338880 байт.

Итоговый runtime-wheel собран в `runtime-wheel-final/`, исходники внутри сверены с рабочим деревом, лицензия сохранена, установка в отдельном окружении и pip check прошли. Отдельный короткий CPU-only тест из установленного wheel без PyTorch/SymPy/Hailo выполнил обе реализации на партиях до 128 блоков под лимитом 768 МиБ, swap=0. Пик RSS GNU time — 58168 КиБ (около 56.80 МиБ), OOM не зарегистрирован. NumPy 1.26.4 для автономной проверки переиспользован через локальные symlink. Это x86 проверка памяти, не измерение ARM и не память всей системы.

На Raspberry Pi скорость ещё не измерялась. Перед статьёй необходимы независимые процессы для каждого backend, контроль частот/температуры/PCIe, несколько ключей и корпусов r, интервальные оценки и решение о native/multicore CPU-baseline. Текущее совместное чередование backend сохраняет сопоставимость с существующим бенчмарком ПК, но не заменяет этот расширенный протокол. Энергопотребление и устойчивость к побочным каналам не измерялись.
